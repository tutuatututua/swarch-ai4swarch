# งานที่ 2: เขียน ADR สำหรับความต้องการใหม่ (ประมาณ 20 นาที)

> **เชื่อมโยงกับการบรรยาย:** T3 (GPT-4 แบบ zero-shot ให้ผลที่สอดคล้องกัน แต่ *ครบถ้วนน้อยกว่ามนุษย์* ส่วน few-shot ช่วยลดช่องว่างได้มาก), AICH3 (บริบท), สัปดาห์ที่ 10 (message broker)
> **คำถาม:** ADR ที่ AI เขียนดีขึ้นแค่ไหน เมื่อให้ตัวอย่างและบริบทจริงแก่ AI

อ่าน [สถานการณ์ (ภาษาไทย)](../docs/scenario.th.md) ก่อน: ความต้องการ **R-12** ว่าด้วยสิ่งที่เกิดขึ้นหลังจากลูกค้าสั่งซื้อสินค้า

ในแต่ละ run ให้เริ่ม **แชตหรือ session ใหม่** แล้วส่งข้อความด้านล่าง โดยแทนที่ `<paste R-12 here>` ด้วยข้อความ R-12 ภาษาอังกฤษที่อยู่ในกรอบอ้างอิงของ scenario

**Run a: ไม่มีตัวอย่าง (zero-shot)** → [`outputs/2a-adr.md`](outputs/2a-adr.md)
```
Follow prompts/2-write-adr.md
run: a
context: none
requirement: <paste R-12 here>
language: Thai
```

**Run b: มีตัวอย่าง + บริบท** → [`outputs/2b-adr.md`](outputs/2b-adr.md)
```
Follow prompts/2-write-adr.md
run: b
context: docs/scenario.md, docs/adr/0001-use-redis-for-cart-storage.md, system/online-boutique/src/checkoutservice/main.go
requirement: <paste R-12 here>
language: Thai
```

> บรรทัด `language: Thai` ทำให้ agent เขียน ADR เป็นภาษาไทย (หัวข้อของ template และชื่อทางเทคนิคยังคงเป็นภาษาอังกฤษ) หากต้องการภาษาอังกฤษให้ลบบรรทัดนี้ **ใช้ภาษาเดียวกันทั้ง Run a และ Run b** เพื่อให้เปรียบเทียบกันได้

> ใน Run a ให้ตรวจว่า agent ไม่ได้อ่านไฟล์อื่นนอกจาก template จริง ๆ หาก agent เปิด `docs/scenario.md` ให้บันทึกไว้ใน prompt log เพราะจะทำให้การเปรียบเทียบเปลี่ยนไป

## เปรียบเทียบ a กับ b

อ้างอิง: **a** = `exercise/outputs/2a-adr.md`, **b** = `exercise/outputs/2b-adr.md` (เลขหลัง `:` คือบรรทัด); ตรวจตัวเลขกับ `docs/scenario.md:24–30`

| เกณฑ์ | Run a | Run b |
|---|---|---|
| ใช้ตัวเลขจาก scenario หรือไม่ | ใช้ครบ: checkout p95 ≤ 500 ms (เดิมประมาณ 300 ms), พีก 200 คำสั่งซื้อ/วินาที; MailFast p95 1.5 วินาที, p99 8 วินาที, ล้มเหลว 0.5%, จำกัด 50 อีเมล/วินาที (`a:17–18`) | ใช้ตัวเลขเดียวกัน และนำไปกำหนดเกณฑ์ทดสอบ (`b:17–18,74`) |
| ทางเลือกที่พิจารณา | synchronous; ฐานข้อมูลกับ worker; outbox กับ RabbitMQ — เลือกข้อ 3 (`a:38–54`) | synchronous ผ่าน gRPC; worker กลาง; outbox กับ RabbitMQ — เลือกข้อ 3 (`b:36–50`) |
| แต้มครั้งเดียวและ rate limit | ใช้ unique order ID บันทึกการรับเหตุการณ์และเพิ่มแต้มในธุรกรรมเดียว แล้ว ACK หลัง commit; จำกัด MailFast รวมทุก replica และ retry ≤ 50 อีเมล/วินาที (`a:61–62`) | ใช้กลไกเดียวกัน และเพิ่ม request idempotency key ป้องกันคำขอสั่งซื้อเดิมซ้ำ (`b:55–56,68`) |
| มีสิ่งที่แต่งขึ้นเองหรือไม่ | ตัวเลขหลักตรงกับ scenario; outbox และกลไก retry ระบุเป็นข้อเสนอใหม่ (`a:17–20,56–63`) | พีกนาน 60 วินาทีเป็นตัวอย่าง [Inferred]; outbox และ idempotency key เป็นข้อเสนอใหม่ (`b:52,65,68`) |

**ข้อควรระวัง:** Run a ใช้ข้อมูล scenario เกินกรอบ R-12 (`a:11–20`; `docs/scenario.md:9–14`) จึงยังเปรียบเทียบตามเงื่อนไข zero-shot เดิมไม่ได้ ต้องทำ Run a ใหม่ในแชตใหม่โดยให้เฉพาะ R-12 และ template หากต้องการผลเปรียบเทียบตรงโจทย์

Run b อ้างโค้ดที่สร้าง UUID ใหม่เพื่อชี้ปัญหาคำขอซ้ำ (`b:68`; `system/online-boutique/src/checkoutservice/main.go:233–236`) ส่วน Run a ระบุการกัน analytics ซ้ำชัดกว่า (`a:63`; `b:52–56`) ทั้งสองยังเป็นข้อเสนอและยังไม่มีผลทดสอบ (`a:79`; `b:72`)

## รับผิดชอบ ADR ฉบับสุดท้ายของตัวเอง

นิสิตคือสถาปนิก ให้คัดลอก `outputs/2b-adr.md` ไปที่ `docs/adr/0002-<short-title>.md` แล้วแก้ไข**ด้วยตัวเอง**จนพร้อมจะลงชื่อรับรอง ห้ามให้ agent ทำส่วนนี้

- แก้ไขสิ่งที่ผิดหรือแต่งขึ้นเอง และเพิ่มสิ่งที่ขาดหายไป
- ตัดสินใจขั้นสุดท้ายด้วยตัวเอง นิสิตสามารถไม่เห็นด้วยกับ AI ได้

นิสิตจะต้องปกป้อง ADR นี้ต่อหน้าคณะกรรมการรีวิวในส่วน B จึงต้องอธิบายทุกการตัดสินใจใน ADR ได้

| # | สิ่งที่เปลี่ยนจากร่างของ AI | เหตุผล |
|---|---|---|
| 1 | เอาตัวอย่างที่สมมติว่าพีกนาน 60 วินาทีออก รวมถึงจำนวนงานค้างและเวลาระบายคิวที่คำนวณจากตัวอย่างนั้น | โจทย์ไม่ได้บอกว่าช่วงพีกนานเท่าไร จึงยังใช้ตัวเลขนั้นกำหนดขนาดคิวจริงไม่ได้ |
| 2 | เพิ่มวิธีกัน analytics บันทึกคำสั่งซื้อเดิมซ้ำ โดยใช้ `event_id` และ ACK หลังบันทึกสำเร็จ | เมื่อได้รับข้อความเดิมอีก ระบบต้องไม่เพิ่มยอดนับซ้ำ |
| 3 | ใส่ชื่อในช่อง `Deciders` จากที่ยังไม่ได้ระบุชื่อ | เปลี่ยนชื่อว่าใครเป็นผู้ตัดสินใจและรับผิดชอบสำหรับ step ถัดไป |

# ADR-0002: แยกงานหลังสั่งซื้อผ่าน RabbitMQ พร้อมบันทึกเหตุการณ์อย่างทนทาน

- **Status:** Proposed
- **Date:** 2026-10-25
- **Deciders:** ยังไม่ระบุผู้มีอำนาจตัดสินใจ

## Context and problem

เอกสารนี้ใช้ `docs/scenario.th.md` เป็น requirement โดยไม่มีไฟล์ context เพิ่มเติม ข้อมูลระบบปัจจุบันมาจากสถานการณ์ที่โจทย์กำหนด ยังไม่ได้ตรวจสอบกับ source code

| ข้อเท็จจริงจาก requirement | หลักฐาน |
|---|---|
| หลังสั่งซื้อ ต้องส่งอีเมลผ่าน MailFast แทน logic จำลองของ `emailservice` ให้แต้มผ่าน `loyaltyservice` ใหม่ และบันทึกเหตุการณ์ analytics; ปีหน้าคาดว่าจะเพิ่ม SMS, fraud scoring และการอัปเดตระบบแนะนำสินค้า | `docs/scenario.th.md` — ความต้องการใหม่ (R-12) |
| ปัจจุบัน `checkoutservice.PlaceOrder` เรียก `paymentservice`, `shippingservice` แล้วจึงเรียก `emailservice` แบบ synchronous ผ่าน gRPC; อีเมลล้มเหลวแล้วบันทึก warning แต่คำสั่งซื้อยังสำเร็จ | `docs/scenario.th.md` — ระบบทำงานอย่างไรในปัจจุบัน |
| p95 ของ `PlaceOrder` ต้องไม่เกิน 500 ms ปัจจุบันประมาณ 300 ms; ช่วงพีก 200 คำสั่งซื้อ/วินาที | `docs/scenario.th.md` — เป้าหมายด้านคุณภาพและข้อจำกัด: Checkout latency, ปริมาณงานช่วงพีก |
| MailFast มี p95 1.5 วินาที, p99 8 วินาที, ล้มเหลวประมาณ 0.5% และจำกัด 50 อีเมล/วินาที | แหล่งเดียวกัน — MailFast |
| แต้มต้องได้รับภายใน 1 นาทีและไม่ซ้ำ; คำสั่งซื้อต้องไม่ล้มเหลวเพราะอีเมล แต้ม หรือ analytics ล่ม | แหล่งเดียวกัน — แต้มสะสม, ความพร้อมใช้งาน |
| ทีม 4 คนถนัด Go/gRPC มี 2 คนเคยใช้ RabbitMQ; ระบบรันบน Kubernetes และบริษัทชอบ open-source ที่ติดตั้งเอง | แหล่งเดียวกัน — ทีม, การปฏิบัติการ |

**[Inferred]** การรอ MailFast ในเส้นทางตอบกลับ checkout เสี่ยงเกินงบ latency แต่ยังคำนวณ p95 รวมอย่างแม่นยำไม่ได้จาก percentile ของแต่ละส่วนเพียงอย่างเดียว (หลักฐาน: `docs/scenario.th.md` — Checkout latency, MailFast)

รายละเอียดที่เก็บคำสั่งซื้อ ธุรกรรม และ API ของ MailFast: Not evidenced in the provided files จึงไม่ถือว่าระบบมี outbox หรือรองรับ idempotency อยู่แล้ว

## Decision drivers

1. **Availability:** งานหลังสั่งซื้อล่มต้องไม่ทำให้คำสั่งซื้อล้มเหลว
2. **Performance:** p95 ของ `PlaceOrder` ≤ 500 ms ที่ 200 คำสั่งซื้อ/วินาที
3. **Correctness และ timeliness:** ให้แต้มเพียงครั้งเดียวภายใน 1 นาที
4. **Modifiability:** เพิ่มงานหลังสั่งซื้อในอนาคตได้โดยลดการแก้ checkout
5. **Operability และ cost:** ทีมดูแลได้บน Kubernetes โดยคำนึงถึงประสบการณ์ RabbitMQ

หลักฐาน: `docs/scenario.th.md` — R-12 และเป้าหมายด้านคุณภาพและข้อจำกัด; การจัดลำดับเป็นข้อเสนอของ ADR นี้

## Considered options

1. เรียก MailFast, `loyaltyservice` และ analytics แบบ synchronous จาก checkout พร้อม timeout และจัดการข้อผิดพลาด
2. บันทึกงานลงฐานข้อมูลอย่างทนทาน แล้วให้ worker ดึงงานไปทำโดยไม่ใช้ message broker
3. บันทึกเหตุการณ์ด้วย transactional outbox แล้วกระจายผ่าน RabbitMQ ไปยัง consumer แยกตามงาน

ทั้งสามทางเลือกเป็นแบบที่เสนอ ไม่ใช่ข้อยืนยันโครงสร้างระบบปัจจุบัน การประเมินต่อไปนี้เป็น **[Inferred]** จากข้อจำกัดใน `docs/scenario.th.md` — R-12 และเป้าหมายด้านคุณภาพและข้อจำกัด

### Pros and cons of the options

| Option | Pros | Cons |
|---|---|---|
| 1 — synchronous | ใช้ทักษะ Go/gRPC ของทีม; ลำดับการเรียกเข้าใจง่าย; ไม่เพิ่ม broker | การรอ MailFast เสี่ยงเกิน 500 ms; timeout ไม่รับประกันว่างานจะสำเร็จ; ต้องเพิ่มการเก็บงานและ retry เพื่อทนต่อปลายทางล่ม; งานใหม่เพิ่ม coupling กับ checkout |
| 2 — ฐานข้อมูลและ worker | แยก latency ปลายทางออกจาก checkout; บันทึกงานร่วมกับผลสั่งซื้อในธุรกรรมเดียวได้หากออกแบบที่เก็บให้รองรับ; ไม่ต้องดูแล broker | ต้องสร้างกลไก polling, locking, retry และการกระจายงานเอง; polling เพิ่มเวลารอและภาระฐานข้อมูล; งานใหม่ต้องเพิ่มการจัดการสถานะงาน |
| 3 — outbox และ RabbitMQ | แยก consumer และคิวต่อประเภทงาน; เพิ่มผู้รับเหตุการณ์ได้; ใช้ประสบการณ์ RabbitMQ ของทีม; broker ล่มชั่วคราวแล้วเก็บเหตุการณ์รอส่งได้ | เพิ่ม broker, ที่เก็บ outbox และงานปฏิบัติการ; ต้องจัดการเหตุการณ์ซ้ำและ schema; ยังแก้เพดานอัตราส่ง MailFast ไม่ได้ |

## Decision

เสนอเลือก **ทางเลือก 3** เพื่อแยกงานที่ช้าและล้มเหลวได้ออกจาก checkout และรองรับงานใหม่ตาม R-12 โดยใช้ RabbitMQ แบบติดตั้งเองบน Kubernetes ให้สอดคล้องกับทักษะและแนวทางปฏิบัติการของทีม (`docs/scenario.th.md` — R-12, ทีม, การปฏิบัติการ)

รายละเอียดต่อไปนี้เป็น **ข้อเสนอใหม่** ที่ต้องนำไปออกแบบและตรวจสอบ ไม่ใช่โครงสร้างที่พบจากไฟล์ระบบ:

- เมื่อยืนยันผลสั่งซื้อสำเร็จ ให้บันทึกผลสำเร็จและเหตุการณ์ `OrderPlaced` ลงที่เก็บถาวรในธุรกรรมเดียวด้วย transactional outbox ก่อนตอบสำเร็จ ห้ามใช้การบันทึกผลและส่ง broker เป็นสองขั้นตอนอิสระที่อาจทำเหตุการณ์สูญหาย ที่เก็บและขอบเขตธุรกรรมจริงยังต้องตรวจสอบตาม **Open questions**
- ให้ relay ส่ง outbox เข้า RabbitMQ ด้วย persistent messages, durable queues ที่มีการจำลองข้อมูล และ publisher confirms; ทำเครื่องหมายส่งแล้วหลังยืนยันเท่านั้น หากส่งซ้ำให้ consumer รับมือได้ Checkout ไม่รอ broker หรือ consumer
- ใช้คิวแยกสำหรับอีเมล แต้ม และ analytics เพื่อให้ backlog ของงานหนึ่งไม่กีดขวางอีกงาน กำหนด event ID, order ID, เวลาสั่งซื้อ และ schema version ที่คงที่; ตกลงข้อมูลที่ผู้รับจำเป็นต้องใช้ก่อนพัฒนา
- ปรับ `emailservice` เป็น consumer ที่ส่งผ่าน MailFast แทน logic จำลอง จำกัดอัตรารวมทุก replica ไม่เกิน 50 อีเมล/วินาที รวม retry; ใช้ backoff และ jitter พร้อมคิวตรวจสอบข้อความที่ผิดถาวรโดยไม่ทิ้งเงียบ
- ให้ `loyaltyservice` บังคับ unique key ตาม order ID สำหรับการให้แต้มชนิดนี้ และบันทึกการรับเหตุการณ์พร้อมเพิ่มแต้มในธุรกรรมเดียว Ack หลัง commit เท่านั้น หาก crash หลัง commit แล้วได้รับข้อความซ้ำ ต้องตรวจพบและไม่เพิ่มแต้มอีก เป้าหมายคือผลทางธุรกิจเกิดครั้งเดียวบนการส่งแบบ at-least-once ไม่อ้างว่า broker ส่งครั้งเดียว
- ให้ consumer ของ analytics ป้องกันเหตุการณ์ซ้ำด้วย event ID และ ack หลังบันทึกสำเร็จ สำหรับ MailFast ต้องตรวจสอบความสามารถ idempotency ก่อนกำหนดการ retry เมื่อเกิด timeout ที่ไม่ทราบผล

**[Inferred]** Outbox ลดการพึ่งพา broker ขณะ checkout แต่เพิ่มการพึ่งพาที่เก็บถาวรและเวลาเขียนข้อมูล การเขียนต้องอยู่ภายในงบ latency และต้องกำหนดการกู้คืนเมื่อ payment/shipping มีผลแล้วแต่บันทึกผลสำเร็จไม่ได้ (รายละเอียดฐานข้อมูลและขอบเขตธุรกรรมเดิม: Not evidenced in the provided files)

## Consequences

- **Positive:** **[Inferred]** การไม่รอ MailFast และ consumer ช่วยลดผลกระทบต่อ checkout จาก latency และการล่มของปลายทาง แต่ต้องพิสูจน์ด้วยการทดสอบ — คุณลักษณะ: performance, availability; หลักฐานเป้าหมาย: `docs/scenario.th.md` — Checkout latency, MailFast, ความพร้อมใช้งาน
- **Positive:** **[Inferred]** คิวแยกและสัญญา `OrderPlaced` ช่วยให้เพิ่มงานใหม่ด้วยการเพิ่ม consumer — คุณลักษณะ: modifiability; หลักฐานความต้องการ: `docs/scenario.th.md` — R-12
- **Negative:** **[Inferred]** เพิ่มภาระดูแล broker, outbox, retry, schema และการกู้คืนให้ทีม 4 คน — คุณลักษณะ: operability, cost; หลักฐานข้อจำกัด: `docs/scenario.th.md` — ทีม, การปฏิบัติการ
- **Negative:** **[Inferred]** ผู้ใช้เห็นคำสั่งซื้อสำเร็จก่อนอีเมล แต้ม และ analytics เสร็จ จึงต้องจัดการ eventual consistency — คุณลักษณะ: consistency, usability; หลักฐานขอบเขตงาน: `docs/scenario.th.md` — R-12, แต้มสะสม
- **Risks and mitigations:** **[Inferred]** หากหนึ่งคำสั่งซื้อใช้อีเมลหนึ่งฉบับ พีก 200 รายการ/วินาทีเทียบกับเพดาน 50 ฉบับ/วินาทีทำให้ backlog เพิ่มอย่างน้อย 150 ฉบับ/วินาทีขณะพีกต่อเนื่อง แม้ยังไม่รวม retry; RabbitMQ เพียงเก็บงานรอ ต้องทราบระยะพีกและเวลาส่งอีเมลที่ยอมรับได้ก่อนกำหนดความจุหรือเจรจา quota — คุณลักษณะ: capacity, timeliness, cost; หลักฐาน: `docs/scenario.th.md` — ปริมาณงานช่วงพีก, MailFast
- **Risks and mitigations:** **[Inferred]** เหตุการณ์ซ้ำอาจทำให้ได้แต้มซ้ำ ใช้ unique key และธุรกรรมฝั่ง `loyaltyservice` ตามข้อเสนอ พร้อมทดสอบ crash/replay — คุณลักษณะ: correctness; หลักฐานเป้าหมาย: `docs/scenario.th.md` — แต้มสะสม
- **Risks and mitigations:** **[Inferred]** relay, broker หรือ `loyaltyservice` ล่มนานเกินเส้นตายทำให้ให้แต้มภายใน 1 นาทีไม่ได้ แม้คำสั่งซื้อยังสำเร็จ ต้องติดตามอายุเหตุการณ์ตั้งแต่เวลาสั่งซื้อ เตือนก่อนผิดเป้าหมาย และตกลงงบ outage กับแผนกู้คืน; คิวไม่รับประกันเส้นตายด้วยตัวเอง — คุณลักษณะ: availability, timeliness; หลักฐานเป้าหมาย: `docs/scenario.th.md` — แต้มสะสม, ความพร้อมใช้งาน

## Open questions

- ใครเป็นผู้ตัดสินใจ และจะทบทวน ADR เมื่อใด?
- เก็บผลคำสั่งซื้อที่ใด และทำธุรกรรมร่วมกับ outbox อย่างไร? หากต้องเพิ่มที่เก็บใหม่ ทีมยอมรับเทคโนโลยีและภาระดูแลใด? จะกู้คืนอย่างไรหาก payment/shipping มีผลแล้วแต่บันทึกผลสำเร็จไม่ได้?
- ช่วงพีก 200 คำสั่งซื้อ/วินาทีนานเท่าใด ปริมาณปกติเท่าใด และอีเมลกับ analytics ยอมรับความล่าช้าได้เท่าใด? เพิ่ม quota MailFast ได้หรือไม่?
- ข้อกำหนดแต้มภายใน 1 นาทีครอบคลุม outage แบบใดและนานเท่าใด? วิธีคำนวณแต้ม ตัวระบุสมาชิก และพฤติกรรมเมื่อยกเลิกคำสั่งซื้อเป็นอย่างไร?
- MailFast ใช้ protocol และ authentication ใด รองรับ idempotency key หรือการตรวจสอบผลหลัง timeout หรือไม่ และจำกัดอัตราในหน้าต่างเวลาแบบใด?

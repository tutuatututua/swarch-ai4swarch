# ADR-0002: ใช้ RabbitMQ แยกงานหลังการสั่งซื้อออกจาก checkout

- **Status:** Proposed
- **Date:** 2026-10-25
- **Deciders:** ยังไม่ระบุในไฟล์ที่ให้มา ดู Open questions

## Context and problem

R-12 กำหนดให้ส่งอีเมลผ่าน MailFast แทน logic จำลองใน `emailservice` ให้แต้มผ่าน `loyaltyservice` ใหม่ และบันทึกเหตุการณ์ analytics หลังสั่งซื้อ โดยคาดว่าจะเพิ่ม SMS การประเมินทุจริต และการอัปเดตคำแนะนำสินค้าในปีหน้า (หลักฐาน: `docs/scenario.md` หัวข้อ The new requirement (R-12); `docs/scenario.th.md` หัวข้อ ความต้องการใหม่ (R-12)).

ปัจจุบัน `PlaceOrder` เรียกชำระเงิน จัดส่ง และอีเมลตามลำดับผ่าน gRPC; แม้อีเมลล้มเหลวจะบันทึกเพียงคำเตือนและยังตอบสำเร็จ แต่ต้องรอการเรียกอีเมลจบก่อนตอบ (หลักฐาน: `system/online-boutique/src/checkoutservice/main.go` บรรทัด 252–279 และสัญลักษณ์ `chargeCard`, `shipOrder`, `sendOrderConfirmation`).

| ประเด็น | ข้อเท็จจริงและหลักฐาน |
|---|---|
| latency และปริมาณงาน | `PlaceOrder` ต้องมี p95 ≤ 500 ms จากปัจจุบันประมาณ 300 ms; พีก 200 คำสั่งซื้อ/วินาที (`docs/scenario.md`, Quality goals and constraints แถว Checkout latency และ Peak load) |
| MailFast | p95 1.5 วินาที, p99 8 วินาที, ล้มเหลวประมาณ 0.5%, จำกัด 50 อีเมล/วินาที (ไฟล์เดียวกัน แถว MailFast) |
| แต้มและความพร้อมใช้งาน | ให้แต้มภายใน 1 นาที ครั้งเดียวเท่านั้น; คำสั่งซื้อห้ามล้มเหลวเพราะอีเมล แต้ม หรือ analytics ล่ม (ไฟล์เดียวกัน แถว Loyalty points และ Availability) |
| ทีมและการปฏิบัติการ | นักพัฒนา 4 คน ถนัด Go/gRPC; 2 คนเคยใช้ RabbitMQ; ใช้ Kubernetes และต้องการ open-source ที่ติดตั้งเอง (ไฟล์เดียวกัน แถว Team และ Operations) |

[Inferred] การรอ MailFast ในเส้นทางตอบกลับเสี่ยงเกินเป้า 500 ms จาก latency ที่กำหนด แต่ไม่อาจคำนวณ p95 รวมด้วยการบวก p95 แต่ละบริการ หากหนึ่งคำสั่งซื้อต้องส่งหนึ่งอีเมล ช่วงพีกต่อเนื่องจะมีงานค้างเพิ่มอย่างน้อย 200 − 50 = 150 รายการ/วินาที ก่อนนับ retry (คำนวณจาก `docs/scenario.md` แถว Peak load และ MailFast).

## Decision drivers

1. **ความพร้อมใช้งาน:** แยกความล้มเหลวของงานหลังสั่งซื้อออกจากผลคำสั่งซื้อ (`docs/scenario.md` แถว Availability).
2. **ความถูกต้องและความทันเวลา:** แต้มไม่ซ้ำและได้ภายใน 1 นาที (ไฟล์เดียวกัน แถว Loyalty points).
3. **ประสิทธิภาพ:** รักษา p95 ≤ 500 ms ที่ 200 คำสั่งซื้อ/วินาที พร้อมเคารพเพดาน MailFast 50 อีเมล/วินาที (ไฟล์เดียวกัน แถว Checkout latency, Peak load และ MailFast).
4. **ความสามารถในการปรับเปลี่ยน:** รองรับงานใหม่ในอนาคต (ไฟล์เดียวกัน หัวข้อ R-12).
5. **ภาระดูแลและต้นทุน:** เหมาะกับทีม 4 คนและ Kubernetes โดยใช้ประสบการณ์ RabbitMQ ที่มี (ไฟล์เดียวกัน แถว Team และ Operations).

## Considered options

ตัวเลือกต่อไปนี้เป็นข้อเสนอใหม่ ข้อดีข้อเสียเป็น [Inferred] จากรูปแบบที่เสนอและข้อจำกัดข้างต้น ไม่ใช่คำอธิบายระบบที่ติดตั้งแล้ว

1. เรียกอีเมล แต้ม และ analytics แบบ synchronous ผ่าน gRPC พร้อม timeout และบันทึกข้อผิดพลาด
2. บันทึกงานอย่างคงทน ให้ worker กลางดึงไปเรียกบริการผ่าน gRPC และติดตามสถานะแต่ละงาน
3. บันทึกคำสั่งซื้อพร้อม outbox แล้วกระจายเหตุการณ์ผ่าน RabbitMQ ไปยังคิวแยกตามงาน

### Pros and cons of the options

| Option | Pros | Cons |
|---|---|---|
| 1. เรียกแบบ synchronous | ใช้ทักษะ gRPC เดิม; เพิ่มโครงสร้างพื้นฐานน้อย | รอ MailFast เสี่ยงเกินเป้า latency; timeout แล้วทิ้งงานไม่รับประกัน R-12; เพิ่มงานต้องแก้ checkout; retry ยังต้องป้องกันแต้มซ้ำ |
| 2. ใช้ worker กลางกับแหล่งเก็บงาน | นำงานออกจากเส้นทางตอบกลับ; เก็บสถานะและ retry ได้; ใช้ gRPC เดิมต่อได้ | ต้องสร้างการจัดตาราง จองงาน และกู้คืนเอง; เพิ่มงานต้องแก้ตัวประสานงาน; ต้องแยกกำลังประมวลผลเพื่อไม่ให้อีเมลค้างขวางแต้ม |
| 3. ใช้ outbox และ RabbitMQ | แยกคิว การ retry และกำลังประมวลผลต่อประเภทงาน; เพิ่มผู้รับเหตุการณ์ได้; สอดคล้องกับประสบการณ์ทีมและการติดตั้งเอง | เพิ่ม broker และแหล่งเก็บข้อมูลคงทนให้ดูแล; ต้องรองรับข้อความซ้ำและ schema; ความคงทนเพิ่มภาระและ latency ที่ต้องวัด |

## Decision

เลือก **ตัวเลือก 3: outbox และ RabbitMQ** เพื่อแยกงานที่มี latency และเพดานต่างกัน รองรับงานใหม่ตาม R-12 และใช้ประสบการณ์ทีม (`docs/scenario.md`, R-12 และแถว MailFast, Team, Operations). รายละเอียดต่อไปนี้เป็นข้อเสนอให้พัฒนา:

- ให้ checkout บันทึกสถานะยอมรับคำสั่งซื้อและเหตุการณ์ `OrderPlaced` ในธุรกรรมเดียวกันของแหล่งเก็บข้อมูลคงทนใหม่ก่อนตอบสำเร็จ แล้วให้ตัวส่ง outbox ทำงานแยกจากคำขอ ไม่รอผู้รับเหตุการณ์ ทั้งนี้ `system/online-boutique/src/checkoutservice/main.go` บรรทัด 230–280 ยังไม่แสดงการบันทึกคำสั่งซื้อหรือ outbox; เทคโนโลยีแหล่งเก็บข้อมูลและจุด commit ต้องตกลงตาม Open questions
- ให้ตัวส่งเผยแพร่โดยรอ publisher confirm แล้วจึงทำเครื่องหมายส่งแล้ว ใช้ข้อความ persistent และคิว durable แบบทำสำเนาบน RabbitMQ ใน Kubernetes; เมื่อ broker ล่มให้เก็บ outbox รอ retry โดยไม่ทำให้คำสั่งซื้อที่บันทึกสำเร็จแล้วล้มเหลว กำหนด topology และทรัพยากรจากการทดสอบ
- กระจายเหตุการณ์ไปยังคิวอีเมล คิวแต้ม และคิว analytics แยกกัน ให้ `emailservice` รับงานและใช้ MailFast แทน logic จำลอง ให้ `loyaltyservice` ใหม่รับงานแต้ม และให้ตัวรับ analytics บันทึกเหตุการณ์ตาม R-12; โปรโตคอล API ของ MailFast และปลายทาง analytics ยังไม่ปรากฏในหลักฐาน (`docs/scenario.md`, R-12)
- ออกแบบการส่งแบบ at-least-once ใช้ `event_id` เดิมตลอด retry และผูกกับ `order_id` ให้ `loyaltyservice` บันทึกการประมวลผลและรายการเพิ่มแต้มในธุรกรรมเดียวกัน พร้อม unique constraint ตามคำสั่งซื้อและประเภทการให้แต้ม แล้วจึง ACK เพื่อให้ผลเพิ่มแต้มเกิดครั้งเดียวแม้รับข้อความซ้ำ; RabbitMQ เพียงอย่างเดียวไม่ใช่การรับประกันผล exactly-once
- จำกัดการเรียก MailFast รวมทุก worker และ retry ไม่เกิน 50 ครั้ง/วินาที แยก retry พร้อม backoff และที่พักข้อความที่ล้มเหลวซ้ำสำหรับตรวจสอบ/ส่งใหม่ เฝ้าระวังอายุคิวแต้มและแจ้งเตือนก่อนเกิน 1 นาที; ค่า timeout, retry และ retention ยังต้องตกลง (ข้อจำกัด: `docs/scenario.md` แถว MailFast และ Loyalty points)

[Inferred] การแยกคิวช่วยไม่ให้คิวอีเมลขวางแต้ม แต่ไม่อาจรับประกันให้แต้มภายใน 1 นาทีเมื่อ `loyaltyservice` ล่มเกิน 1 นาที ต้องยืนยันเงื่อนไขข้อกำหนดก่อนอ้างว่าผ่านครบทุกเป้าหมาย (`docs/scenario.md` แถว Loyalty points และ Availability).

## Consequences

- **Positive:** [Inferred] ลดเวลาที่ checkout ต้องรอบริการหลังสั่งซื้อ และให้บริการเหล่านั้นล่มได้โดยคำสั่งซื้อที่บันทึกสำเร็จยังสำเร็จ (คุณลักษณะ: ประสิทธิภาพและความพร้อมใช้งาน; เป้าหมายจาก `docs/scenario.md` แถว Checkout latency และ Availability; กลไกตาม Decision).
- **Positive:** [Inferred] เพิ่มตัวรับงานใหม่ผ่านเหตุการณ์และคิวแยก ลดการแก้ checkout (คุณลักษณะ: ความสามารถในการปรับเปลี่ยน; อ้างอิง `docs/scenario.md`, R-12 และข้อเสนอใน Decision).
- **Negative:** [Inferred] เพิ่มภาระสำรองข้อมูล กู้คืน เฝ้าระวัง และจัดการ schema ให้ทีม 4 คน; ธุรกรรมบันทึกคำสั่งซื้อเพิ่มงานในเส้นทางตอบกลับ (คุณลักษณะ: ต้นทุน ความสามารถในการดูแล และประสิทธิภาพ; อ้างอิง Decision และ `docs/scenario.md` แถว Team).
- **Negative:** [Inferred] อีเมลรอคิวช่วงพีก: หากพีกนาน 60 วินาทีจะค้างอย่างน้อย 9,000 รายการ และใช้เวลาอย่างน้อย 180 วินาทีเพื่อระบายเมื่อไม่มีงานใหม่หรือ retry ต้องตกลงเวลาส่งอีเมลที่ยอมรับได้ (คุณลักษณะ: ความทันเวลาและความจุ; เป็นตัวอย่างคำนวณจาก `docs/scenario.md` แถว Peak load และ MailFast ไม่ใช่ระยะพีกที่ระบุไว้).
- **Risks and mitigations:** [Inferred] การล่มหลังบันทึกแต่ก่อน publish หรือหลัง publish แต่ก่อนทำเครื่องหมายอาจทำให้ส่งซ้ำ ใช้ outbox, confirm และการตรวจซ้ำแบบธุรกรรมตาม Decision พร้อมทดสอบจุดล่มเหล่านี้ (คุณลักษณะ: ความคงทนและความถูกต้อง).
- **Risks and mitigations:** [Inferred] แหล่งเก็บคำสั่งซื้อ/outbox ใหม่ยังเป็น dependency ของ checkout ต้องออกแบบการกู้คืน; outbox แยก broker ออกจากคำขอแต่ไม่ได้รับประกันความพร้อมใช้งานเมื่อแหล่งเก็บนี้ล่ม (คุณลักษณะ: ความพร้อมใช้งานและความคงทน; อ้างอิงข้อเสนอใน Decision).
- **Risks and mitigations:** [Inferred] `PlaceOrder` สร้าง UUID ใหม่ทุกครั้ง (หลักฐาน: `system/online-boutique/src/checkoutservice/main.go` บรรทัด 233–236) จึงเสนอเพิ่ม request idempotency key ที่คงเดิมและบันทึกผลเพื่อคืนคำสั่งซื้อเดิมเมื่อ retry มิฉะนั้นการตรวจซ้ำด้วย `order_id` ป้องกันได้เฉพาะเหตุการณ์ซ้ำของคำสั่งซื้อเดียว การชำระเงินและจัดส่งยังอยู่นอกธุรกรรม outbox จึงต้องกำหนดการกู้คืนระหว่างขั้นตอน (คุณลักษณะ: ความถูกต้องและความสามารถในการกู้คืน; หลักฐานลำดับ: ไฟล์เดียวกัน บรรทัด 252–279).

## Validation

รายการต่อไปนี้เป็นแผนตรวจสอบ ยังไม่ได้รันหรือยืนยันผลของข้อเสนอ:

1. ทดสอบ 200 คำสั่งซื้อ/วินาที พร้อมจำลอง MailFast ตาม p95 1.5 วินาที, p99 8 วินาที และข้อผิดพลาด 0.5%; ตรวจ p95 ของ `PlaceOrder` ≤ 500 ms และการเรียก MailFast รวมทุก worker/retry ≤ 50 ครั้ง/วินาที (เกณฑ์: `docs/scenario.md` แถว Checkout latency, Peak load และ MailFast).
2. วัดเวลาจากยอมรับคำสั่งซื้อจน commit แต้มให้ไม่เกิน 60 วินาทีต่อคำสั่งซื้อ ภายใต้เงื่อนไข outage ที่จะตกลง; ส่งเหตุการณ์ซ้ำและหยุด worker ก่อน/หลัง commit แต่ก่อน ACK ตรวจว่ามีผลเพิ่มแต้มเพียงครั้งเดียว (เกณฑ์: ไฟล์เดียวกัน แถว Loyalty points).
3. ปิดอีเมล แต้ม และ analytics แยกกัน แล้วปิด broker; ตรวจว่าคำสั่งซื้อที่บันทึกสำเร็จยังตอบสำเร็จ งานค้างยังอยู่ และทำงานต่อได้หลังฟื้น หยุดตัวส่ง outbox ก่อน/หลัง confirm แล้วตรวจว่างานไม่หาย (เกณฑ์: ไฟล์เดียวกัน แถว Availability และความคงทนตาม Decision).
4. จำลองคำขอเดิมซ้ำและการล่มระหว่างชำระเงิน จัดส่ง และ commit; ตรวจความสอดคล้องของคำสั่งซื้อกับ outbox และผลแต้ม ใช้ผลยืนยันแบบกู้คืนก่อนใช้งาน (จุดเสี่ยง: `system/online-boutique/src/checkoutservice/main.go`, `PlaceOrder` บรรทัด 233–279).
5. ตรวจว่าทุกคำสั่งซื้อที่สำเร็จมีงานอีเมล แต้ม และ analytics ติดตามได้ ตรวจอายุคิว retry และการส่งงานจากที่พักกลับเข้าคิว พร้อมทดสอบ backlog ตามระยะพีกและเวลาส่งอีเมลที่จะตกลง (ความครบถ้วนจาก `docs/scenario.md`, R-12).

## Open questions

ข้อมูลต่อไปนี้ยังไม่ปรากฏในไฟล์ที่ให้มา:

- ใครมีอำนาจตัดสินใจและรับผิดชอบดูแล broker กับแหล่งเก็บข้อมูลใหม่? ไม่ใช้รายชื่อผู้ตัดสินใจของ ADR-0001 แทนโดยไม่มีหลักฐาน (`docs/adr/0001-use-redis-for-cart-storage.md`, Deciders).
